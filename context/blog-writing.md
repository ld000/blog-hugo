# Blog Writing Guide

这个文件记录博客写作时需要长期遵守的语气、结构和方法。写新文章或改旧文章前，先读这里，再结合具体主题和历史文章判断。

## 写作定位

博客整体是个人技术笔记，不是营销号、官方文档或课程讲义。文章应该像一个工程师把自己真正理解、实践、踩坑后的东西整理出来，读者能快速知道：

- 这篇文章解决什么问题。
- 为什么这个问题值得单独写。
- 关键概念或步骤之间是什么关系。
- 什么时候适用，什么时候不用上这个复杂度。

整体风格更接近技术文档化的个人笔记：结论明确、结构清楚、少讲写作缘起。可以保留个人判断，但不要让文章变成“我看了什么 / 我觉得什么”的读后感。

## 语气

- 中文为主，语气朴素、直接、技术人写给技术人。
- 保留作者原有的实操感，不要把文字改成过度正式、过度流畅的通用技术媒体腔。
- 少写空泛判断，多写具体场景、具体原因、具体边界。
- 文章开头直接进入问题和判断，不要用“最近看了一个视频/文章/资料：xxx”这类来源先行的句子；来源放到文末“参考”即可。
- 来源只放在文末“参考”，正文不写“视频里提到”“这篇文章说到”这类来源转述句。需要引用观点时，改写成文章自己的判断。
- 可以有主观判断，但优先写成明确判断句，少用“我觉得”“我的理解是”。例如写“不要一开始就默认上全套”，而不是“我的理解是，不要一开始就默认上全套”。
- 不写夸张营销表达，比如“彻底颠覆”“必学神器”“保姆级教程”。
- 不故意文学化，不用大段情绪化铺垫。

### 开头写法

开头要先回答“读者为什么要读这篇”。推荐从困惑、边界或一句话结论进入。

不要这样写：

```md
最近看了一个视频：[Stop Confusing LangChain, LangGraph, and LangSmith]，讲的是这三个东西到底分别是什么。
```

可以这样写：

```md
LangChain、LangGraph、LangSmith 这几个名字很容易混在一起。它们不是同一层的东西：LangChain 管组件，LangGraph 管流程，LangSmith 管运行可见性。
```

也可以这样写：

```md
很多 AI 工程栈介绍会把 LangChain、LangGraph、LangSmith 放在一起讲，但真正选型时，关键不是“要不要都用”，而是先判断系统复杂度到了哪一层。
```

开头通常包含：

- 问题：读者正在困惑什么。
- 判断：这篇文章会给出什么区分方式。
- 边界：什么场景需要读，什么场景不用上复杂度。

## 常用文章类型

### 解释型文章

适合介绍概念、工具、框架、技术栈关系。

推荐结构：

```md
开头：困惑 / 一句话结论 / 判断边界
## 从最简单的场景开始
## 核心概念 1
## 核心概念 2
## 核心概念 3
## 它们怎么一起工作
## 什么时候需要，什么时候不需要
## 总结
## 参考
```

写法重点：

- 先用一两段把结论压出来，再展开。读者应该在开头就知道文章的判断框架。
- 先从读者已经熟悉的简单场景开始，再逐步加复杂度。
- 每个概念都回答“它解决什么问题”，而不是只解释官方定义。
- 概念之间要讲关系，例如谁负责组件、谁负责流程、谁负责观测。
- 一定要写“不需要它的场景”，避免文章变成全家桶推荐。

以 `LangChain, LangGraph, LangSmith 是什么` 这类文章为例，推荐节奏是：

```md
这几个名字为什么容易混
一句话区分三者
从一次模型 API 调用开始
复杂度如何从 API 调用变成 pipeline / agent
分别解释每个工具解决的问题
三者怎么组合
什么时候需要，什么时候不需要
参考
```

判断句要有适用边界。少写：

```md
LangGraph 很重要。
```

多写：

```md
当 agent 开始出现分支、循环、状态和人工审批时，LangGraph 才会明显有价值。
```

### 教程型文章

适合工具配置、环境搭建、操作步骤。

推荐结构：

```md
## 背景
## 准备
## 操作步骤
## 验证
## 常见问题
## 总结
```

写法重点：

- 步骤要可复现。
- 命令和配置要完整。
- 截图或图示要放在对应步骤附近。
- 最后说明如何验证成功。

### 排障型文章

适合 bug、线上问题、源码分析。

推荐结构：

```md
## 软件版本 / 环境
## 问题现象
## 初步怀疑
## 排查过程
## 根因分析
## 解决方案
## 总结
```

写法重点：

- 保留排查路径，不要只给结论。
- 关键日志、代码、SQL、调用链要贴出来。
- 说明哪些猜测被排除了。
- 结论要能让读者迁移到自己的问题上。

## 配图方法

解释型文章不要只放少量点缀图，而要尽量用图说清楚内容。图片应该承担讲解任务，让读者扫图也能串起主线。

### 技术图的任务类型

每张图先确定它要解决什么问题，再决定画法。优先使用这四类：

- 关系图：解释几个概念、工具、模块之间的层次和职责。
- 流程图：解释一次请求、一次任务或一个 agent 如何一步步流转。
- 决策图：解释什么场景需要什么工具，什么场景不需要。
- 边界图：解释框架解决什么，不解决什么，生产系统还缺哪一层。

一张图只承担一个主要任务，不要同时画关系、流程、决策和边界。图里的文字负责标注结构，正文负责展开解释。

如果已经有 SVG 承担结构表达，正文不要再用 `text` 代码块画同一张图。`text` 图只适合保留很短的代码式定义，例如 `用户输入 -> 调用模型 API -> 返回文本`；复杂流程、循环、架构关系交给 SVG。

适合配图的位置：

- 概念关系：几个工具、模块、角色之间的关系。
- 流程变化：从简单 API 调用到完整系统。
- Pipeline：输入、检索、上下文组装、模型、输出。
- 循环和分支：agent 的 ReAct loop、条件边、状态流转。
- 架构图：端到端请求路径。
- 选型表：什么时候需要，什么时候不需要。
- 生产边界：认证、授权、审计、租户隔离等非框架问题。

配图风格：

- 优先使用 SVG 技术图，中文清晰、可维护、可 diff。
- 深色图风格贴合站点和根目录 `DESIGN.md`：背景接近 `#010102`，面板用 `#0f1011`，细线、低对比辅助文字，少量使用 `#5e6ad2` 作为强调色。
- 图里的文字要短，负责表达结构，不要塞大段正文。
- 每张图都要有明确 alt 文本，Markdown 引用放在解释它的段落附近。
- SVG 中的特殊字符要转义，例如 `&` 写成 `&amp;`。

技术图文字规则：

- 主标题只写图的结论，不重复文章标题。
- 节点文字尽量控制在 12 个中文字符以内。
- 一个节点最多两行说明；需要解释原因时放到正文。
- 同一篇文章里的图使用同一套颜色、字号、圆角、线宽和字体。
- 状态色不要做成红黄绿仪表盘；除非状态本身是重点，否则用灰阶和单一强调色区分层级。

以 `LangChain, LangGraph, LangSmith 是什么` 这类解释型文章为例，推荐保留这些核心图：

- 三层关系图：先建立 `LangChain / LangGraph / LangSmith` 的职责边界。
- 简单调用 vs 系统复杂度：说明为什么不是一开始就需要框架。
- RAG pipeline：把“应用系统”拆成可见步骤。
- LangGraph agent 流程图：把 ReAct 循环、条件边和共享状态合并表达，避免两张图讲同一件事。
- LangSmith trace 图：说明可观测性解决什么问题。
- 决策图或生产边界图：帮助读者判断什么时候需要全套，什么时候还需要额外工程层。

如果一篇文章里图片超过 8 张，优先检查是否有两张图在重复表达同一个结论。能合并成一张更清楚的流程图时，就不要把读者的注意力切得太碎。

## 命名和目录

新文章目录采用：

```text
年-序号-文章名
```

例如：

```text
content/ai/2026-2-langchain-langgraph-langsmith/
```

规则：

- 年份使用文章年份。
- 序号按同一年、同分区内已有文章顺序递增。
- 文章名部分使用小写、英文、URL 友好命名。
- 有多张图或本地资源时，使用 page bundle：`content/<section>/<slug>/index.md`，资源放 `assets/`。

## Front Matter

AI 相关文章默认放在 `content/ai/`，常用 front matter：

```yaml
---
title: "文章标题"
date: 2026-05-09
tags: ["AI"]
categories: ["AI"]
series: ["AI 手记"]
description: 简短说明文章解决什么问题
---
```

description 要具体，不要只重复标题。

## 修改和验收

- 写作前先看相关历史文章，保持作者声音一致。
- 改文章时保持编辑聚焦，不顺手改标题、日期、slug、标签，除非任务要求。
- 内容或配置变更后，尽量运行：

```bash
hugo --gc --minify
```

- 如果 Hugo 清理了 `resources/` 里的生成缓存，不把这类构建副作用作为源码修改保留。
- SVG 配图新增或修改后，用 XML parser 校验，避免裸 `&` 等解析错误。
