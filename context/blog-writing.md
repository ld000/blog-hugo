# Blog Writing Guide

这个文件记录博客写作时需要长期遵守的语气、结构和方法。写新文章或改旧文章前，先读这里，再结合具体主题和历史文章判断。

## 写作定位

博客整体是个人技术笔记，不是营销号、官方文档或课程讲义。文章应该像一个工程师把自己真正理解、实践、踩坑后的东西整理出来，读者能快速知道：

- 这篇文章解决什么问题。
- 为什么这个问题值得单独写。
- 关键概念或步骤之间是什么关系。
- 什么时候适用，什么时候不用上这个复杂度。

## 语气

- 中文为主，语气朴素、直接、技术人写给技术人。
- 保留作者原有的实操感，不要把文字改成过度正式、过度流畅的通用技术媒体腔。
- 少写空泛判断，多写具体场景、具体原因、具体边界。
- 可以有主观判断，但要说明判断依据，例如“我的理解是”“比较适合”“不建议一开始就上全套”。
- 不写夸张营销表达，比如“彻底颠覆”“必学神器”“保姆级教程”。
- 不故意文学化，不用大段情绪化铺垫。

## 常用文章类型

### 解释型文章

适合介绍概念、工具、框架、技术栈关系。

推荐结构：

```md
## 背景 / 为什么会有这个问题
## 从最简单的场景开始
## 核心概念 1
## 核心概念 2
## 核心概念 3
## 它们怎么一起工作
## 什么时候需要，什么时候不需要
## 总结
## 参考
```

写法重点：

- 先从读者已经熟悉的简单场景开始，再逐步加复杂度。
- 每个概念都回答“它解决什么问题”，而不是只解释官方定义。
- 概念之间要讲关系，例如谁负责组件、谁负责流程、谁负责观测。
- 一定要写“不需要它的场景”，避免文章变成全家桶推荐。

### 教程型文章

适合工具配置、环境搭建、操作步骤。

推荐结构：

```md
## 背景
## 准备
## 操作步骤
## 验证
## 常见问题
## 总结
```

写法重点：

- 步骤要可复现。
- 命令和配置要完整。
- 截图或图示要放在对应步骤附近。
- 最后说明如何验证成功。

### 排障型文章

适合 bug、线上问题、源码分析。

推荐结构：

```md
## 软件版本 / 环境
## 问题现象
## 初步怀疑
## 排查过程
## 根因分析
## 解决方案
## 总结
```

写法重点：

- 保留排查路径，不要只给结论。
- 关键日志、代码、SQL、调用链要贴出来。
- 说明哪些猜测被排除了。
- 结论要能让读者迁移到自己的问题上。

## 配图方法

解释型文章不要只放少量点缀图，而要尽量用图说清楚内容。图片应该承担讲解任务，让读者扫图也能串起主线。

适合配图的位置：

- 概念关系：几个工具、模块、角色之间的关系。
- 流程变化：从简单 API 调用到完整系统。
- Pipeline：输入、检索、上下文组装、模型、输出。
- 循环和分支：agent 的 ReAct loop、条件边、状态流转。
- 架构图：端到端请求路径。
- 选型表：什么时候需要，什么时候不需要。
- 生产边界：认证、授权、审计、租户隔离等非框架问题。

配图风格：

- 优先使用 SVG 技术图，中文清晰、可维护、可 diff。
- 深色图风格贴合站点：背景接近 `#0f0f0f` / `#111111`，细线、低对比辅助文字，少量强调色。
- 图里的文字要短，负责表达结构，不要塞大段正文。
- 每张图都要有明确 alt 文本，Markdown 引用放在解释它的段落附近。
- SVG 中的特殊字符要转义，例如 `&` 写成 `&amp;`。

## 命名和目录

新文章目录采用：

```text
年-序号-文章名
```

例如：

```text
content/ai/2026-2-langchain-langgraph-langsmith/
```

规则：

- 年份使用文章年份。
- 序号按同一年、同分区内已有文章顺序递增。
- 文章名部分使用小写、英文、URL 友好命名。
- 有多张图或本地资源时，使用 page bundle：`content/<section>/<slug>/index.md`，资源放 `assets/`。

## Front Matter

AI 相关文章默认放在 `content/ai/`，常用 front matter：

```yaml
---
title: "文章标题"
date: 2026-05-09
tags: ["AI"]
categories: ["AI"]
series: ["AI 手记"]
description: 简短说明文章解决什么问题
---
```

description 要具体，不要只重复标题。

## 修改和验收

- 写作前先看相关历史文章，保持作者声音一致。
- 改文章时保持编辑聚焦，不顺手改标题、日期、slug、标签，除非任务要求。
- 内容或配置变更后，尽量运行：

```bash
hugo --gc --minify
```

- 如果 Hugo 清理了 `resources/` 里的生成缓存，不把这类构建副作用作为源码修改保留。
- SVG 配图新增或修改后，用 XML parser 校验，避免裸 `&` 等解析错误。
